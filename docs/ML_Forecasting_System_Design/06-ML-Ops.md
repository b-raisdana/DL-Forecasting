# ML-Ops

Practices for running experiments on this project's own hardware — resource monitoring, throughput/cost profiling. Not production/serving MLOps: see [99-Exclusion.md § MLOps / Infrastructure](99-Exclusion.md#mlops--infrastructure) for that boundary.

## Training-run resource monitoring

The single 8GB GPU is the binding constraint ([03 § hardware constraints](<03-Model & Architecture Engineering.md#hardware-constraints>)), so every training run needs a real-time signal on which resource is actually limiting it. Concrete implementation already exists — `ResourceSampler` in [train.py](<../../app/ai_modelling/tier1_000/train.py>): a background thread polling `GPUtil` + `psutil` every 2s during `model.fit()` (Keras callbacks only fire between steps, missing usage *during* a step's compute). This section sets the KPIs/thresholds its output should be judged against, and the follow-up diagnostic once one is crossed.

Follows Brendan Gregg's **USE Method** (Utilization/Saturation/Errors, per resource) — the KPI table below covers Utilization for each resource; most Saturation/Error signals are still missing and called out separately in [saturation & error signals](#saturation--error-signals-not-yet-in-the-kpi-table) rather than bloating the table.

### KPI table

| resource     | metric / source                                                                                                                     | healthy                                                    | warning                                       | critical                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------- | ---------------------------------------------- | --------------------------------------------- |
| GPU compute  | `gpu_util_percent` (`GPUtil` `gpu.load×100`; cross-check `nvidia-smi dmon -s u`) — a coarse "kernel active" sample, not true throughput; see caveat below | mean ≥85% during steady-state steps — GPU should be the bottleneck, not idle | 50–85% mean, or spiky (alternating near-0%/high) | <50% mean                                     |
| VRAM         | `gpu_mem_used_mb`/`_total_mb` (`GPUtil`) + `tf.config.experimental.get_memory_info("GPU:0")` current/peak                            | peak <85% of card total (8188MiB)                          | 85–95% peak                                    | >95% peak, or any OOM                         |
| system RAM   | `psutil.virtual_memory().used` + `process_rss_mb`                                                                                    | <85% of the WSL2-visible total used — **~47GB on this box** (raised from a ~31GB default cap via `.wslconfig`, not the host's full 64GB), see note below | 85–95%                                          | >95%, or any `psutil.swap_memory()` activity  |
| CPU          | `psutil.cpu_percent()` (ideally `percpu=True`; 32 logical cores on this box, `nproc`)                                                | low-moderate — feeding the GPU, not competing with it        | one core pegged ~100% while GPU util is also low | sustained high across many cores while GPU idles, or `os.getloadavg()[0]` > core count (>32 here) |
| disk I/O     | `psutil.disk_io_counters()` deltas → MB/s + IOPS (**not yet sampled**, see gap below)                                                | ~0 sustained reads during steady-state steps                | any sustained non-zero read after the data-build phase | —                                             |

85% is used as both a floor (GPU compute — want it high) and a ceiling (VRAM/RAM — want headroom), matching this project's own evidence: `batch_size=8` ran a full clean 10-minute training loop at ~76% peak VRAM, `batch_size=16` OOM'd mid-run at ~98% peak (both on the RTX 4060 Laptop 8GB/WSL2 card — see [train.py](<../../app/ai_modelling/tier1_000/train.py>)'s finding, also noted in [model.py](<../../app/ai_modelling/tier1_000/model.py>)'s `TIER1_000_CONFIG`). The real fragmentation boundary sits between those two numbers, so 85% is the reasonable line for "validate against a full-length run before trusting this batch size" rather than a short burst — a short burst hides BFC-allocator fragmentation that only surfaces after many varying-shape steps. Caveat: those are the only two real data points measured so far (one clean, one OOM) — treat 85% as an interpolated estimate, not a proven boundary, and re-tighten it once more batch sizes get profiled.

**RAM ceiling correction (found + fixed 2026-08-16):** [03 § hardware constraints](<03-Model & Architecture Engineering.md#hardware-constraints>) states "64GB RAM," which is the Windows host's physical RAM (`Get-CimInstance Win32_ComputerSystem` confirms ~63.7GB) — but training actually runs inside WSL2 ([CLAUDE.md § Python environment](<../../CLAUDE.md>)), and WSL2 was only exposing **~31GB** to that process (`free -h` inside `Ubuntu-24.04`: 31Gi total, 8Gi swap), roughly half, with no `.wslconfig` override present (WSL2's undocumented-but-standard default cap, not a deliberate choice). Fixed: `C:\Users\<user>\.wslconfig` now sets `[wsl2]` `memory=48GB` (applied via `wsl --shutdown`; WSL was fully stopped at the time, so nothing in-progress was interrupted) — `free -h` post-restart confirms ~47GB total, swap auto-scaled to 12GB, GPU passthrough unaffected (`nvidia-smi` still sees the RTX 4060 Laptop, 8188MiB). This still leaves ~16GB for the Windows host plus the `AlmaLinux-9`/`docker-desktop` WSL distros also sharing this same VM-wide memory pool (`wsl -l -v`) — raise further only if the host itself starts feeling memory-pressured. [03 § vram/ram budget split](<03-Model & Architecture Engineering.md#vramram-budget-split>)'s "~65% in-memory feature/candle cache" line can now be re-derived off ~48GB (≈31GB cache) instead of the old ~31GB ceiling (≈20GB cache) — closer to, though still under, the original 64GB-based plan (≈42GB).

**GPU-utilization caveat:** `nvidia-smi`/`GPUtil`'s `utilization.gpu` is a coarse ~1Hz "was any kernel active during this sample" signal, not a measure of SM occupancy or FLOPs throughput — a run can show a high percentage while still being far from compute-saturated. It's the right cheap first-line KPI (matches what this doc scopes to), but don't over-read small differences (e.g. 67% vs. 85%) as precise compute-efficiency deltas; [`tf.profiler`](#collection-tooling)'s step-level device-time breakdown is the authoritative source once that distinction actually matters.

### current status against these KPIs

Tier1_000's first live run (2026-08-15, `batch_size=8`, 10 min, BTCUSDT): mean GPU util 29% (max 67%) — **below** the 85% target — peak VRAM 76% (**within** target), CPU ~3% (**within** target). The low GPU util is a known, already-diagnosed tradeoff, not a fresh alarm: VRAM capped the batch size at 8, and a small batch leaves real GPU parallelism on the table even when the input pipeline is perfectly fed — CPU ~3% rules out an input-pipeline stall as the cause.

### diagnosing low GPU utilization

Low GPU util alone doesn't say why — cross-reference against CPU and disk simultaneously:

- low GPU + high/pegged CPU → CPU-bound input pipeline (feature computation, heavy `tf.data` `.map()`) → precompute/cache features, more `.prefetch(tf.data.AUTOTUNE)`/parallel `.map()` calls, move preprocessing off the hot path.
- low GPU + low CPU + no disk I/O → the GPU itself is stalling for a non-input reason: batch too small (this project's current case), Python/eager-mode overhead between steps, or a `.numpy()`/sync call inside the training loop forcing a device sync.
- low GPU + ongoing disk reads during steady state → a caching bug, not a hardware ceiling: per [03 § vram/ram budget split](<03-Model & Architecture Engineering.md#vramram-budget-split>) the dataset should be RAM-resident after `build_dataset()`'s initial load, so per-step disk reads during training mean something is bypassing that RAM cache — same class of bug the [cache-or-generate skill](<../../.claude/skills/cache-or-generate/SKILL.md>) targets, not a "faster disk" problem.
- GPU util degrading gradually over a long run (not at the start) → suspect thermal throttling, not a code-side regression — this is a *laptop* GPU, which (unlike a desktop card) clocks down under sustained thermal load; check `gpu.temperature` (`GPUtil`) or `nvidia-smi --query-gpu=temperature.gpu,clocks.sm --format=csv`.

### saturation & error signals (not yet in the KPI table)

The KPI table's warning/critical columns are Utilization thresholds. The USE Method's other two signals catch failure modes utilization alone can miss — none of these are sampled by `ResourceSampler` yet; listed here as the concrete next additions rather than folded into the table:

- **CPU saturation** — `os.getloadavg()` (1/5/15-min load average): a load average above the core count (>32 here) means processes are queued waiting for CPU, a stronger "CPU is the bottleneck" signal than `cpu_percent()` alone, which can look moderate even when the run queue is backed up.
- **RAM saturation** — already covered: `psutil.swap_memory()` activity (KPI table, critical column) is the correct saturation signal for memory under the USE method.
- **VRAM saturation** — no clean equivalent metric exists (NVML doesn't expose an allocation-retry counter); an OOM exception itself is the de facto saturation signal, already the critical trigger in the KPI table.
- **Errors** — nothing currently checked. Two cheap additions, each a single `subprocess.run(["dmesg", ...])` call: `dmesg | grep -i "killed process"` (Linux OOM-killer silently terminating a worker process — looks like a run that just stopped, with no VRAM/RAM percentage necessarily near 100% at the moment it happened) and `dmesg | grep -i xid` (NVIDIA Xid errors — driver-level GPU faults, e.g. from thermal/power issues on this laptop card). Worth running on any run that dies without a clear Python-level exception.

### disk I/O — WSL2 caveat

The repo lives under `/mnt/c/Code/DL-Forecasting` — the Windows filesystem accessed through WSL2's 9p/virtiofs translation layer, meaningfully slower than native ext4 for small/random reads. Rule that out ("is this the translation tax, not real disk hardware") before concluding disk itself is the bottleneck.

### collection tooling

- **in-process (built)**: `ResourceSampler` in [train.py](<../../app/ai_modelling/tier1_000/train.py>) — extend with `psutil.disk_io_counters()` deltas, `psutil.cpu_percent(percpu=True)`, `os.getloadavg()`, and `psutil.swap_memory().percent` to close the current sampling gaps.
- **lower-overhead GPU sampling (optional upgrade)**: `GPUtil` shells out to `nvidia-smi` via `subprocess` on every poll (2×/sec here) and is effectively unmaintained; `nvidia-ml-py`/`pynvml` (NVIDIA's own NVML bindings) call the driver in-process instead, at lower per-poll cost, and expose temperature/power-draw/clocks too (the thermal-throttling check above currently has to shell out to `nvidia-smi` separately for those). `nvitop` (below) is itself built on this.
- **richer live terminal view**: `nvitop` — `htop`, but for the GPU: a live TUI covering per-process GPU util/mem/temp/power plus host CPU/RAM in one screen; run it in a spare WSL2 terminal alongside training as a nicer alternative to `watch -n1 nvidia-smi`. `gpustat` is a lighter, one-shot/loopable CLI if a full TUI is unnecessary.
- **external GPU cross-check**: `nvidia-smi dmon -s u` — useful since NVML queries occasionally fail transiently under WSL2 GPU passthrough (`train.py`'s poll loop already retries past this).
- **disk I/O detail, if `psutil` counters aren't enough**: `iostat -x 1` (Linux `sysstat` package) adds await-latency and queue-depth per device — `psutil.disk_io_counters()` only gives cumulative bytes/ops, so on its own it can show "some I/O happened" without saying whether it's actually slow.
- **root-cause tool once a KPI is flagged**: TensorFlow's own profiler (`tf.profiler.experimental.start()`/`.stop()`, or TensorBoard's `profile_batch=`) gives a step-level trace that splits input-pipeline wait time from device compute time directly — heavier-weight than the psutil/GPUtil poller, so reach for it only after the KPI table flags a problem, not as an always-on monitor.

### reporting

Every run already logs `ResourceSampler.summary()` in its `report` dict (`run_training()`'s return value). It's only useful longitudinally — is this run's GPU util worse than last week's, for the same config? — once it's persisted somewhere other than stdout; that's the same experiment-tracking gap [`docs/todos/03-infrastructure.md` todo #1](<../todos/03-infrastructure.md>) already owns, not a new one.

- **live view during a run**: log each `ResourceSampler` sample as `tf.summary.scalar` (a `tf.summary.create_file_writer()` alongside the existing Keras `TensorBoard` callback) — reuses the same profiler stack already named under [collection tooling](#collection-tooling) above instead of adding a new dependency, and gives a live-updating chart in TensorBoard while `model.fit()` is still running.
- **cross-run persistence**: write `ResourceSampler.summary()` (and, space permitting, the raw per-sample series) to whatever backend the MLflow-vs-CSV/SQLite decision lands on ([`docs/todos/03-infrastructure.md` todo #1](<../todos/03-infrastructure.md>)) — same artifact, not a separate store.
- **Alt: Prometheus + Grafana — rejected.** Built for continuously-running services scraped over long uptimes across many hosts, with alerting for an ops team; this project is a single researcher on one machine running bounded (10min–few hr) training sessions, no fleet, nothing to page. Standing up two persistent Docker services to view one job's metrics is disproportionate, and would duplicate the still-undecided MLflow/SQLite choice above rather than resolve it — same class of infrastructure sprawl [99-Exclusion.md § MLOps / Infrastructure](<99-Exclusion.md#mlops--infrastructure>) already rules out. Revisit only if training moves to multiple concurrent/remote machines.
